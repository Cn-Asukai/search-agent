# 汉化检索优化

把汉化检索做成「作品身份解析 + 多渠道发现 + 证据判定 + 持续更新」，而不是「让模型多搜几次」。

准确率、覆盖率、效率不必总是互相牺牲。别名整理得更好，既能减少误判，也能减少无效搜索；证据缓存做得好，既能加快查询，也能避免重复推理。

本文是设计建议，不绑定某次实现。收益和预算要用样本验证。配置项（如 `mode: engine`、`network: china`、`steps: 8`）是仓库当前状态的观察，不代表运行时已经实测出对应故障。

相关实现：[`prompts/hanhua-search.md`](../prompts/hanhua-search.md)、[`src/domain/search.ts`](../src/domain/search.ts)、[`websearch.config.yaml`](../websearch.config.yaml)、[`opencode.jsonc`](../opencode.jsonc)。架构见 [`architecture.md`](architecture.md)。

## 用户真正要的不是一个「有 / 没有」

一次汉化检索包含几个不同问题：

1. **作品是谁？** 同名作品、不同译名、漫画改编、小说原作不能混淆。
2. **有没有中文内容？** 中文介绍、中文目录、中文正文不是一回事。
3. **是什么中文版本？** 官方出版、民间翻译、机器翻译、机翻润色。
4. **覆盖多少？** 一话试译、部分卷数、全本翻译。
5. **现在还能不能获取？** 曾经发布过，不代表链接现在有效。
6. **是否仍在更新？** 长期没更新，不等于明确弃坑。

把「版本存在」「当前可访问」「翻译进度」「更新状态」分开。例如：

> 已确认该漫画存在繁体中文民间翻译，至少发布至第 12 话；原发布页目前无法访问，存在转载证据；是否仍在更新未知。

这比「有汉化，中等置信度」更能帮助用户，也更不容易误导。

## 当前设计里优先调整的点

| 当前实现 | 潜在问题 | 建议 |
|---|---|---|
| 提示词允许用标题精确一致的条目确认作品 | 同名作品、原作与改编可能混在一起 | 精确标题作为候选命中，再核对作者、媒介或其他身份特征 |
| `official.exists`、`fan.exists` 都是布尔值 | 无法表达「官方确认有，民间还没查清楚」 | 两个分支各自保存证据状态 |
| JSON Schema 将 `official` 描述为「仅官方中文」 | 确认官方存在，并不能证明民间不存在 | 结论表述改成「已确认官方中文」；排他性另行表达 |
| 聚合站「能看」通常推断背后有汉化来源 | 可能转载官方译本，不能直接认定民间汉化 | 分开判定「中文正文存在」和「译本来源」 |
| 多轮无结果后允许 `none` | 搜索引擎收录不足、抓取失败可能被解释为没有 | 对外表达「在本次检索范围内未发现」 |
| 提示词最多 10 轮搜索，agent 配置 `steps: 8` | 两种预算没有统一定义，可能无法完成预期流程 | 统一模型步数、搜索调用、抓取调用、时间预算 |
| 配置为 `mode: engine`、`network: china` | 按配置注释，海外引擎覆盖受到限制 | 先确认实际启用的引擎与网络可达性，再评估渠道补充 |

## 精确度：先保证搜的是同一部作品

### 作品身份与别名层

每次检索先得到一个作品身份记录：

- 原名
- 官方中文名、民间常用译名
- 简体、繁体名称
- 罗马字或英文名
- 作者，以及漫画原作 / 作画角色
- 媒介类型
- 已验证的外部条目 ID
- 与原作、改编、外传的关系

规则：

> **别名可以合并，改编关系不能当成别名合并。**

某小说有中文版，不能据此推断其漫画也有汉化。用户没指定类型时，应该分别给出小说和漫画的结论，而不是搜两种、最后塞进一个 `work.type`。

别名也需要记录来源。模型自行翻译出来的中文标题，只能作为**候选查询词**，不能当成已经确认的通用译名。

### 身份匹配：召回宽、确认严

候选发现可以容忍：

- 标点、空格差异
- 全角半角
- 简繁转换
- 副标题省略
- 常见缩写
- 少量输入错误

确认阶段要核对更强特征：

- 作者是否相符
- 小说还是漫画
- 是否外传、续作或重制版
- 出版信息是否一致

不要因为一个作者字段不完整就直接排除：漫画条目可能列作画，小说条目列原作者。要比较角色，而不是机械比较字符串。

### 不要把「中文页面」当成「中文版本」

以下页面只能作为线索：

- 「求汉化」「什么时候汉化」
- 中文剧情介绍
- 只有中文标题的原文资源
- 英文翻译组页面
- 空目录、占位条目
- 宣布取得版权，但尚未发行的公告

确认存在中文内容，应寻找书目信息、正式中文连载页、明确发布记录，或可以核对的中文正文证据。

还要区分：

> **已获授权 ≠ 已发行；已有试译 ≠ 全作汉化；原作完结 ≠ 汉化完结。**

## 证据：每项结论都有依据

`sources` 现在是来源列表，来源和具体结论之间的关系不够明确。按**事实主张**组织证据：

| 事实主张 | 应对应的证据 |
|---|---|
| 官方中文版已出版 | 出版社书目、正式发行记录 |
| 民间翻译曾发布 | 翻译者发布页、署名和发布时间 |
| 已翻译至第 12 话 | 具体目录或章节发布记录 |
| 已完结 | 明确完结说明及其覆盖范围 |
| 已弃坑 | 发布者明确公告，不能仅凭长期未更新 |

一份证据记录至少包括：

- 支持哪一项结论
- 来源 URL
- 原文摘录或可核对位置
- 页面发布时间与抓取时间
- 来自搜索摘要、正文，还是图片识别
- 是否第一手来源
- 是否存在冲突

### 来源可靠性针对「它能证明什么」

不要简单地给整个域名一个总分：

- 出版社适合证明官方发行，但不适合证明民间翻译不存在。
- 汉化组适合证明自己的发布，但未必能证明全网最新进度。
- 聚合站能提供发现线索，但不一定能证明翻译归属。
- 论坛帖子可以证明有人宣布开坑，但不能自动证明已经发布正文。

一个可信第一手来源，可以胜过十个互相转载的页面。交叉验证要看来源是否独立。十个镜像站复制同一份目录，不应算十份独立证据。

### 置信度拆开表达

至少区分：

- 作品身份置信度
- 中文版本存在的证据强度
- 翻译归属置信度
- 进度可信度
- 检索覆盖情况

「确认存在」可以很可靠，「目前最新进度」仍然可能未知。一个总的 `high / medium / low` 容易掩盖这种差异。

## 广泛度：扩大不同的信息入口

不要重复改写同一组查询。

### 查询词按目标生成

不要只循环「作品名 + 汉化 / 中文版 / 翻译」。分成几个查询族：

| 查询目标 | 示例 |
|---|---|
| 身份确认 | `"原名" 作者` |
| 官方中文 | `"中文名" 出版社`、`"原名" 繁體中文版` |
| 民间发布 | `"原名" 汉化`、`"别名" 翻譯` |
| 正文线索 | `"别名" 第1话`、`"别名" 第一卷` |
| 发布者溯源 | `"作品名" "组名"` |
| 最新进度 | `"作品名" 更新`、`"作品名" 完结` |
| 历史线索 | `"作品名" 发布`、旧译名与旧站名组合 |

短标题、常见词标题优先加作者；精确短语没有结果后再放宽。不要一次把所有限定词都堆进去。

繁体检索也不只是简体转繁体。台湾出版译名可能与大陆民间译名完全不同，真正有价值的是译名发现。

### 官方和民间作为两个独立分支

身份确认后：

```text
作品身份
├─ 官方分支：授权、出版、地区、已发行卷数
└─ 民间分支：发布者、正文证据、进度、可访问性
```

不能找到官方出版信息就停止全部检索，否则会漏掉 `both`；也不能找到民间汉化就跳过官方分支。

每个分支独立记录：

- 已确认
- 有线索待核实
- 本次未发现
- 检索受阻

这样「一个分支成功、另一个超时」也能返回真实且有用的部分结果。

### 多引擎要追求新增覆盖

建议先比较：

- 一个中文覆盖较好的渠道
- 一个能补足不同索引覆盖的渠道
- 重点领域站点的站内搜索或公开接口

不要默认所有查询都打所有引擎。衡量某渠道的价值，应看：

> 它额外发现了多少之前没找到、最终被验证的作品或版本？

不是看它返回了多少 URL。供应商轮转主要解决可用性和负载问题，**不等于同一次检索获得多索引覆盖**。

### 网页抓取应允许跟随相关链接

当前提示词仅允许抓取搜索工具已返回的 URL。这能约束乱抓，但也可能卡住：

> 搜索命中作品页 → 作品页链接到目录 → 目录链接到发布公告。

允许跟随已验证页面里的直接相关链接，并限制深度、数量和目标类型。保留「不把搜索结果页当抓取工具搜索入口」的约束。

### 图片和历史页面作为升级路径

漫画证据可能在图片署名或公告图里，纯文本抓取会漏掉。只在关键证据缺失时，对少量相关图片做 OCR / 视觉核对。

历史失效页面可以辅助证明「曾经存在」，但不能证明「当前可访问」。

登录墙、付费限制或访问拒绝，应标记检索受阻，不要解释成没有，也不建议绕过。

## 效率：让每次追加搜索都有理由

### 从自由循环改成受控流程

```text
输入解析 → 身份确认 → 官方/民间并行发现
        → 候选去重 → 定向验证 → 缺口补搜 → 证据汇总
```

代码负责：

- 预算、并发、去重、缓存
- 分支覆盖与停止条件
- 来源引用完整性
- 结果一致性

模型负责：

- 别名理解
- 歧义分析
- 证据解释
- 根据缺口提出下一次查询

这比在提示词里继续追加几十条规则更可控，也不意味着必须立即重写整个 agent。

### 按信息缺口决定下一步

每次继续检索前明确：这次调用要解决什么尚未解决的问题？

- 身份不明 → 查作者与原名
- 已有中文正文但来源不明 → 查署名和发布者
- 官方已确认、民间未覆盖 → 搜民间分支
- 只有最新进度不明 → 查目录，不再重搜所有译名

连续查询只返回相同来源、没有新增证据时，应该停止重复搜索或切换渠道。

「搜了几轮」不是充分性指标，「覆盖了哪些缺口」才是。

### 不同深度模式

| 模式 | 适用目标 | 停止原则 |
|---|---|---|
| 快速 | 尽快判断是否有可靠中文版本线索 | 返回已确认部分，说明未覆盖项 |
| 标准 | 同时检查官方与民间 | 完成主要分支和别名覆盖 |
| 深入 | 冷门作品、疑似漏检、历史资源 | 补充渠道、旧译名、历史线索与溯源 |

不同模式都不能把预算耗尽解释为「不存在」。

### 分层缓存，而不只是保存搜索响应

现有配置已经设置搜索缓存路径。进一步值得做的是：

| 缓存层 | 内容 | 更新策略 |
|---|---|---|
| 作品身份 | 原名、别名、作者、关系 | 较长有效期，纠错时失效 |
| 版本存在事实 | 已验证的发行或发布记录 | 保留历史事实 |
| 当前状态 | 最新进度、可访问性 | 更频繁复查 |
| 未发现结果 | 查询范围与未命中情况 | 较短有效期 |
| 访问失败 | 超时、限流、拒绝访问 | 短暂退避，不进入否定事实 |

尤其重要：

> **曾经确认存在的汉化，不能因为原站下线就变成「没有汉化」。**

用户反复用不同别名查同一作品，应命中同一作品记录。相同作品的并发查询，也应复用正在执行的任务，避免重复外部调用。

### 缩小模型需要阅读的内容

抓取后先提取：

- 作品身份
- 出版、翻译署名
- 目录与更新信息
- 相关证据段落

导航、广告、无关评论不必反复塞进上下文。但保留原始来源与必要上下文，防止截取掉否定语句或适用范围。

当前抓取配置存在「大文本转文件」和内联行数限制，而 agent 禁止读本地文件。**验证两者实际如何配合，避免关键证据只落在 agent 无法访问的文件中。**这属于待验证的接口风险，不是已经确认的故障。

## 长期：积累作品与版本事实

每次检索都从零开始，会反复支付别名发现、身份消歧和证据验证的成本。

逐步积累四类数据：

1. **作品**：规范身份和原作 / 改编关系。
2. **别名**：不同地区、平台、时期的名称及来源。
3. **中文版本**：官方或民间、语言文字、发布者、覆盖范围。
4. **证据与检查记录**：事实依据、检查时间、访问状态。

不需要一开始上图数据库，关系表就可以表达这些关系。

由此可以自然支持：

- 「这个译名其实查过了」
- 「上次到第 12 话，这次是否有新增」
- 「此前未发现，现在出现了发布证据」
- 「原链接失效，但版本存在事实仍成立」

之后再考虑订阅提醒：发现新译本、进度变化、正式发行。提醒应基于**事实变化**，不是模型摘要措辞变化。

## 评测

先做一个人工核实的基准集，建议从 **100～200 部、按难度分层**开始。这是起始规模建议，不是统计充分性的保证。

覆盖：

- 热门与冷门作品
- 只有官方、只有民间、两者都有
- 多译名、同名作品
- 小说有中文但漫画没有已知证据
- 只有英文翻译
- 只有试译、机翻或授权公告
- 聚合站转载官方内容
- 原发布页失效
- 存在事实明确但进度未知

开放网络很难建立「绝对没有」的真值，所以这类样本应标明人工检查范围和日期。

### 核心指标

| 维度 | 指标 |
|---|---|
| 身份准确度 | 是否认对作品与媒介 |
| 存在判定精确率 | 判为有中文的结果中，多少有合格证据 |
| 已知正例召回率 | 基准集中确认存在的版本，找到了多少 |
| 来源分类准确度 | 官方转载是否被误判为民间汉化 |
| 引用支持率 | 引用页面是否真正支持对应结论 |
| 覆盖完整度 | 官方、民间是否分别完成必要检查 |
| 可用性 | 有多少请求得到可行动的答案，而非全部退回未知 |
| 效率 | P50 / P95 延迟、外部调用数、token 与费用 |
| 稳定性 | 同一作品重复查询是否出现无依据的结论变化 |

不要只提高精确率：把所有难题都回答「未知」也能减少误报，却没有产品价值。

改动时做对照实验，分别测：

- 加别名发现
- 加第二个搜索渠道
- 改证据规则
- 加缓存
- 改停止策略

每项优化都看新增有效证据和成本，而不是看输出是不是更长。

## 落地优先级

### 第一阶段：先减少误导性结论

优先改提示词、结果表达与判定规则：

1. 官方 / 民间独立状态，保留未知。
2. 「未发现」不写成绝对没有。
3. 聚合站中文内容不直接等于民间汉化。
4. 同名、原作与改编必须消歧。
5. 进度、完结、弃坑必须有对应证据。
6. 统一搜索、抓取、模型步数和时间预算。

收益：先把「答案说得很确定但依据不够」的风险降下来。

### 第二阶段：提高召回与可验证性

- 别名发现与复用
- 官方 / 民间双分支
- 简繁与地区译名覆盖
- 互补搜索渠道
- 结论到证据的明确关联
- 小型基准集与对照实验

收益：不仅找到更多，还能知道为什么找到了、哪里仍然没覆盖。

### 第三阶段：降低重复成本

- 作品级缓存
- 同作品并发任务复用
- 自适应补搜
- 增量更新目录与链接状态
- 来源独立性去重

收益：已有知识不反复购买，预算留给真正困难的作品。

### 第四阶段：按数据决定是否重投入

再评估：

- 专站适配器
- 图片证据识别
- 历史页面查证
- 订阅更新
- 本地全文或向量检索

不建议现在就优先上向量数据库、全网爬虫或更多 agent。作品名检索首先是**身份、别名和证据问题**；向量检索更适合后续处理「记得剧情但忘了标题」这类语义需求。更多 agent 如果共享同样的查询词和搜索索引，可能只是重复花钱。

---

如果只能先做三件事：**作品身份与别名、官方 / 民间独立证据状态、分层基准集。**

它们分别解决「有没有搜对」「结论能不能信」「优化到底有没有用」。在这三个基础上，再加搜索渠道、并发和缓存，投入才容易转化成可衡量的收益。
